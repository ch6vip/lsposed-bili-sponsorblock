# lsposed-bili-sponsorblock 优化执行计划

## 执行原则

1. 先收口低风险问题，再做结构性重构。
2. 每个任务都要有明确的验收标准，避免“改了但说不清是否完成”。
3. 每完成一个任务，独立提交并推送 GitHub。
4. 先保留现有行为，再替换内部实现，减少回归面。
5. 文档、配置、代码同步更新，避免 UI、Hook、存储三边漂移。

## 当前结论

项目已经具备可用主链路，但仍存在以下长期风险：

- 设置存储逻辑分散，默认值、校验、迁移重复。
- 缓存职责和失效策略有重复实现，后续容易互相打架。
- 菜单注入和宿主页面定位仍依赖经验性兜底，稳定性不足。
- 错误处理和诊断入口不统一，用户只能靠日志排查。
- 核心逻辑缺少最小回归测试，后续改动容易引入隐性 Bug。

## 优化任务清单

### P0 - 先做的稳定性收口

#### 1. R6 缓存职责单一化
- 目标：只保留一层明确的缓存职责，避免 `client` 和 `repository` 同时维护 TTL、失效、强刷逻辑。
- 改动范围：`SponsorBlockClient`、`SponsorBlockRepository`、相关内存缓存与失效调用点。
- 关键动作：
  - 明确谁负责拉取，谁负责缓存。
  - 把 TTL、强刷、命中统计统一到单一层。
  - 删除重复判断和重复日志。
- 验收标准：
  - 同一请求只会命中一套缓存策略。
  - 切集、回看、手动刷新三个场景行为一致。
  - 代码里不再出现两处以上相同的 TTL 逻辑。

#### 2. R8 / T5 诊断与错误处理统一
- 目标：把“失败了只能看日志”改成“用户能看到可定位状态”。
- 改动范围：设置读取、网络请求、提交失败、弹窗提示、设置页状态展示。
- 关键动作：
  - 统一错误类型和错误码。
  - 增加可见状态：读取失败、请求失败、提交失败、权限/配置异常。
  - 关键失败点补上下文日志，但避免高频噪音。
- 验收标准：
  - 用户能在设置页看到当前失败状态。
  - 日志里能定位到失败来源、请求阶段和关键信息。
  - 失败时不会静默吞掉异常。

#### 3. R2 设置通道收口
- 目标：减少对 exported Provider 和目标 App 私有目录直写的隐式依赖。
- 改动范围：设置 Provider、读取入口、写入入口、调用方校验。
- 关键动作：
  - 收紧暴露面。
  - 明确敏感字段和普通字段的处理边界。
  - 补调用方参数校验和失败回退。
- 验收标准：
  - 非法调用不会写入脏配置。
  - 敏感字段的读写路径可追踪。
  - 设置同步不会依赖“碰巧可用”的隐式行为。

### P1 - 结构整理

#### 4. R1 设置存储收敛
- 目标：统一默认值、校验、迁移、序列化。
- 改动范围：`SettingsRepository`、`SettingsSchema`、UI 读取、Hook 读取。
- 关键动作：
  - 把设置定义从页面逻辑里抽出来。
  - 所有默认值只保留一份。
  - 迁移逻辑集中处理。
- 验收标准：
  - UI 和 Hook 读到同一套定义。
  - 修改设置字段时只需要改一处 schema。
  - 历史配置升级不丢值。

#### 5. R3 设置 UI 共用（已完成）
- 目标：让 `LauncherActivity` 和 `SponsorBlockSettingDialog` 共用同一套设置 schema / 行构建器。
- 当前状态：已抽出 `SettingsScreenBuilder`，模块入口和宿主弹窗共用同一套 UI，旧 XML 设置页已移除；模块入口已加入基础状态面板。
- 改动范围：设置分组、行构建、输入校验、颜色选择器、提交配置 UI。
- 关键动作：
  - 抽公共 descriptor。
  - 统一输入控件和错误提示样式。
  - 去掉双实现漂移。
- 验收标准：
  - 模块入口和宿主弹窗展示一致。
  - 新增设置项只需写一次描述。
  - 不再出现某一边修了、另一边没修的问题。

#### 6. R7 菜单注入稳态化
- 目标：减少字段猜测式兜底，提升不同宿主布局下的稳定性。
- 改动范围：`MineMenuInjector`、页面定位、布局识别、回归验证。
- 关键动作：
  - 记录可识别的页面布局特征。
  - 为首页、我的页、深色模式、切账号补验证路径。
  - 降低对“第一个 List 字段”这类脆弱假设的依赖。
- 验收标准：
  - 设置入口在常见页面布局下稳定出现。
  - 新布局不会直接把入口注入逻辑打断。
  - 失败时有明确降级路径。

### P2 - 可维护性与回归

#### 7. R9 / T7 自动化回归
- 目标：把核心逻辑从“手动试”变成“可重复验证”。
- 改动范围：aid/bvid 转换、响应解析、设置快照、跳过决策、最小设备矩阵。
- 关键动作：
  - 补单元测试。
  - 固化回归样例。
  - 给关键决策加断言。
- 验收标准：
  - 核心工具函数有测试覆盖。
  - 关键变更前后可以跑固定回归清单。
  - 新增规则不会无意破坏旧规则。

#### 8. T8 提交体验增强
- 目标：把提交链路从“能提交”提升到“可控、可预览、可分步”。
- 改动范围：分类选择、手动时间编辑、预览确认、投票/反馈拆分。
- 关键动作：
  - 拆分输入和确认阶段。
  - 让时间编辑和分类选择更明确。
  - 明确哪些功能先做、哪些后做。
- 验收标准：
  - 提交流程不会把多个动作混在一起。
  - 预览信息和最终提交内容一致。
  - 功能拆分后入口语义清晰。

#### 9. T2 设置入口稳定性观察
- 目标：把入口是否稳定出现从“印象判断”变成“有记录可回看”。
- 改动范围：首页、我的页、刷新、切账号、深色模式等场景记录。
- 关键动作：
  - 固化观察项。
  - 记录布局条件和结果。
  - 发现问题后回写到注入规则。
- 验收标准：
  - 每个观察场景都有记录。
  - 入口异常能追溯到具体页面状态。

## 推荐执行顺序

1. R6 缓存职责单一化
2. R8 / T5 诊断与错误处理统一
3. R2 设置通道收口
4. R1 设置存储收敛
5. R3 设置 UI 共用（已完成）
6. R7 菜单注入稳态化
7. R9 / T7 自动化回归
8. T8 提交体验增强
9. T2 设置入口稳定性观察

## 完成定义

任一任务完成后，必须同时满足：

- 代码已改完。
- 文档已同步。
- 至少有一种可复现验证方式。
- 单独提交并推送到 GitHub。
